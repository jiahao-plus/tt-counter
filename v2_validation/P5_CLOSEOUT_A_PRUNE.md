## 4. 这是"消除违规扩散区"还是"把有问题的地方删掉"？

这是任务 A 最尖锐的一问。答案不是靠措辞，而是靠一个可判定的测试：

> 若违规是**局部几何特征**的产物（窄段放不下 tap），删掉该特征即根因修复；
> 若违规是**全局属性**的产物（tap 插入策略 / 行铺排 / 站点栅格），
> 删掉受影响区域只是遮掩 —— 同一机制会在别处照样发作。

### 4.1 决定性证据：保留段本身是干净的

保留的 88 段上，第三轮 Magic 报出的 tap/row 违规 = **0**（§3.1）。
若机制是全局的，保留段不可能全干净。

### 4.2 机制本身是可解释的（MEASURED）

Tap 锚定规则（从 997 个真实 tap 反推，`tools/v2_ci_diagnostics/a_threshold_basis.py`）：

```
首 tap 偏移 = 28 站点 = 12.88 µm  （48 个保留段）
            = 56 站点 = 25.76 µm  （40 个保留段）
后续间距    = 56 站点 = 25.76 µm
```

**能容纳 tap 的最小段宽 = 2·O + 1 站点 = 57 站点 = 26.22 µm。**
26 个可删段全部 ≤ 24 站点（10.58 / 7.82 / 11.04 µm）—— 结构上放不下 tap。

**这就是根因**：`cut_rows` 在宏 halo 周围切出的窄条几何上不可能插入 tap，
于是落在里面的单元得不到 tap 覆盖，触发 LU.2/LU.3/nwell.4。
删掉窄条 = 删掉"注定无法合规"的几何，不是把违规掩盖掉。

### 4.3 但必须诚实标注一个反例（MEASURED，且推翻我此前的判断）

| 阶段 | 可删段内的单元 | 非 dummy 单元 |
|---|---|---|
| 19（tap 后） | 52 | **0** |
| 52（fill 后） | 196 | **3 × `conb_1`** |

**3 个 `sky130_fd_sc_hd__conb_1` 常量单元被 placer 放进左碎片 B**，
它们驱动的是真实顶层输出 `uio_oe[5]`、`uio_oe[6]`、`uio_oe[7]`
（`tools/v2_ci_diagnostics/a_conb_probe.py`，final DEF 第 26027/26036/26045 行）。

后果有两条，都必须写进决策：

1. **这 3 个功能单元在剪枝后必须重新放置** → 会扰动布局，不是"纯删空条"。
2. **它们的 `VPB` 在 LVS 里是悬空的**：
   `.rpt` 中 `FILLER_79_9/VPB` 含 `conb_1/VPB = 1`、
   `FILLER_80_9/VPB` 含 `conb_1/VPB = 2`；
   且 `conb_1/VPB` 扇出为 **9 vs 12**（参考侧 12）。
   **所以 R2 不只影响 dummy，也影响功能单元。**
   我此前写的"R2 = 纯物理单元被拆碎"是不完整的，本轮更正。

## 5. 25.76 到底有没有独立物理依据？

### 5.1 实测的安全窗口（MEASURED）

| 量 | 值 |
|---|---|
| 有 tap 的最窄段宽 | **51.06 µm**（111 站点）|
| 无 tap 的最宽段宽 | **11.04 µm**（24 站点）|
|  portanto **安全窗口** | **(11.04 , 51.06]** |

阈值扫描（`tools/v2_ci_diagnostics/a_threshold_basis.py`）：

```
T= 11.05 -> 删 26 段, 丢 tap   0   SAFE
T= 25.76 -> 删 26 段, 丢 tap   0   SAFE
T= 51.06 -> 删 26 段, 丢 tap   0   SAFE
T= 51.07 -> 删 32 段, 丢 tap  10   LOSES TAPS
```

**结论：在 (11.04, 51.06] 这个 40 µm 宽的窗口里，结果完全相同。**

### 5.2 因此 25.76 不是物理常数，是派生量

```
25.76 = 56 站点 = 2 × 28 站点 = 2 × round(FP_TAPCELL_DIST / 0.460)
      = 26.22 µm（57 站点最小可行段）− 0.46 µm
```

它是**派生自 tap 锚定规则**的量，不是独立物理依据。
任务批评"不能依据 Tap X-gap 中位数直接确定阈值"——
严格说 25.76 不是中位数（中位数是 25.76 的 tap 间距本身，巧合相同），
但**批评的实质成立**：这个数没有独立于 tap 规则的物理来源。

### 5.3 它是否仍然可采信？

**可采信，但理由必须换成"窗口内"而非"精确值"：**

- 安全性：`25.76 < 26.22`（最小可行段），所以**结构上不可能删掉能放 tap 的段**
  —— 这一点由 §5.1 的实测窗口独立佐证，不是从公式推的。
- 有效性：`25.76 > 11.04`（最宽死段），所以一定删掉全部 26 段。
- **但换成 12.0、20.0、30.0、50.0 任意一个值，第三轮数据上结果完全相同。**

所以在报告里我不会再写"取 25.76 因为它等于 2·FP_TAPCELL_DIST，语义优美"。
正确的说法是：**在 (11.04, 51.06] 内任取**，25.76 只是其中一个便利值。

| 问题 | 回答 |
|---|---|
| 有独立物理依据吗？ | **没有。** 它是 `2 × round(FP_TAPCELL_DIST/site)` 的派生量 |

## 8. 第四轮前置条件复核（2026-10-29 追加，已写入 config）

用户列出六条必须先确认的前提。本节逐条给出结论与复现命令。
**结论：六条全部满足，`FP_PRUNE_THRESHOLD: 26.22` 已写入 `src/config.json`。**
但按用户要求，报告里它仍是 **PREDICTED_FIX，不是 DRC_PASS**。

### 8.1 第 1 条：LibreLane 是否真的把该变量传给 CutRows

| 测试 | 结果 |
|---|---|
| 是否在 `resolved.json`（411 个声明键）中 | **是**，值为 `None` |
| 是否出现在 `18-openroad-cutrows/_env.tcl` | 否 |
| 是否出现在 `COMMANDS` 命令行 | 否 |

**但这三个"否"是预期的，不是反证。** 追加实验（`c_prune_plumbing.py`）：

```
config.json 中值为 null 的键 : 37 个   -> _env.tcl 中全部缺席
config.json 中非 null 的键   : 57 个   -> _env.tcl 中全部存在
```

`_env.tcl` 是**通用地过滤所有 null 值**，不是专门忽略 `FP_PRUNE_THRESHOLD`。
因此写入一个非 null 值后，它就会出现在 `_env.tcl` 里。
**结论：前置条件 1 由推断满足，而不是由直接执行证据满足**——
本地无 LibreLane 3.0.14，无法跑一次对照实验来直接观察。这一点必须如实标注。

### 8.2 第 2 条：26.22 µm 在制造网格上是否合法

```
站点宽 0.460 µm，行距 2.720 µm
26.22 / 0.46 = 57.0000  （= 2·O+1，O = round(13/0.46) = 28）
合法窗口 = (widest DELETED 11.04, narrowest KEPT 51.06]
```

**阈值比较的是连续段宽，从不吸附到站点网格**，所以 26.22 不需要是整数个站点——
它恰好是，属于巧合而非要求。**满足。**

### 8.3 第 3 条：576/576 的坐标归属能否复现

**能，且是精确复现。** 用 lyrdb 的 **bbox 与段做区间重叠**（不是用质心）：

```
DEL only        576        KEPT only          0
STRADDLES         0        NO-OVERLAP         0
```

**更正一处口径**：先前 `a_prune_physical.py` 用「质心落在段内」归属，
得到 552/576，另有 24 个落在段间空隙。改用 bbox 重叠后 576/576 全部归入，
且**没有任何一条跨越 DEL/KEPT 边界**。质心口径会被 `nwell.4` 的大 bbox 误导。
该脚本里另有「保留段 51 条违规」的 PROXY 模型，**已被否决**：
它量的是「段边缘到最近 tap 的距离」，而 LU.2/LU.3 规则针对的是**扩散区**，
段尾的空站点里没有扩散区。实测 Magic 报的保留段违规是 **0**。见 §8.7。

### 8.4 第 4 条：「丢 Tap 0、丢 Row 0」的准确含义

| 说法 | 精确含义 | 数值 |
|---|---|---|
| 「丢 Row 段」 | 114 个**行段**中删除 26 个 | 26 / 114 |
| 「丢 Row」 | 81 个**制造行**中没有一行失去全部段 | **0 / 81** |
| 「丢 Tap」 | 997 个 `tapvpwrvgnd_1` 中落在删除段内的 | **0 / 997** |
| 「丢已占用标准单元」 | 见下 | 见下 |

> **更正（重要）**：早前 `c_cutrows_model.py` 打印过「Whole fabrication rows
> removed : 1」。那是**坐标轴读反**造成的假象——DEF 的 `ROW <name> <site> <X>
> <Y>` 是 **X 在前**，脚本按 Y 在前读，导致所有几何判据交叉。修正后为 **0 / 81**。
> 该脚本已加入自检（段必须落在 DIEAREA 内、y 必须落在 2.720 网格上），
> 一旦再读反会直接 assert 失败。

**「已占用标准单元」必须分两层看，否则会得出错误结论：**

| 时点 | 段内单元 | 说明 |
|---|---|---|
| 第 18 阶段（CutRows 执行时） | **只有 7 个研究宏**，标准单元数为 0 | 标准单元尚未放置！`COMPONENTS` 头 = 270（全是 I/O 与宏） |
| 第 52 阶段（填充后，最终版图） | **196 个单元** | 177 `decap_3` + 16 `fill_2` + 3 `conb_1` |

所以"丢已占用单元 0"**只在 CutRows 那个时点成立**，不能用来描述最终版图。
真实影响是：这 26 段消失后，196 个 dummy/常量单元无处可放，
其中 **21 个正是 R2 的根源**（见 §8.5），另外 3 个 `conb_1` 需重放。

### 8.5 第 5 条：21 → 0 的关键前提（本轮最关键的一条证据）

要让删除段真的消掉 `device_difference = 21`，必须满足：
**凡是 bulk 悬空的单元，都必须在被删段内。**

`c_floating_bulk_census.py` 的实测结果：

```
class            floating  inPRUNE  outside unmapped
decap_3               164      164        0        0
fill_2                 15       15        0        0
conb_1                  3        3        0        0
fill_1 / tap            0        0        0        0
------------------------------------------------------
TOTAL                 182      182        0        0
```

**182 / 182 全部在被删段内，0 个落在保留段。**

再核对 netgen 的组数（组数 = 该类悬空 VPB 网络数 + 1）：

```
decap_3 悬空 VPB 网络 13 个 -> 13 + 1 = 14   netgen 报 ->14  ✔
fill_2  悬空 VPB 网络  8 个 ->  8 + 1 =  9   netgen 报 ->9   ✔
device_difference = (14-1) + (9-1) = 21                       ✔
```

**这是必要条件，已经满足。它不是充分条件**——仍需真实跑一次 netgen。
关于 3 个 `conb_1`（驱动 `uio_oe[5..7]`）：它们也在被删段内，删除后由布局器重放；
其输出逻辑是 `conb_1` 的常量 `HI`，与其他 9 个 `conb_1` 完全相同，
**功能不依赖具体位置**，因此重放不改变逻辑功能。但其 VPB 是否仍悬空，
取决于新位置是否仍落在窄段——**这一点无法预测，只能说"会变"。**

> **这也纠正了本文档 §6 的一个说法**：那里写"丢失的 dummy（decap/fill）196 个"，
